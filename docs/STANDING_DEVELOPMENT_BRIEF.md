# Standing development brief

## Owner instruction and scope

The owner adopted this brief on 30 October 2026, Australia/Brisbane.
The adoption message states: “Adopt this standing brief and start batch 1.”
It adopts the preceding seven-batch proposal and its authority boundaries.

Develop Lord Cricket XXVI towards the original V0.1 synthetic-alpha release.
Use the original technical design, current architecture and recorded decisions.
Make routine implementation and interface decisions without requesting repeated approval.

## Authorised work

The agent may create branches, implement features, add meaningful tests and fix demonstrated CI failures.
The agent may update documentation, commit, push and open pull requests.
The agent may merge after review and all required checks pass.
Review means inspecting the final diff, compatibility boundaries and actual validation results.
A passing merge does not approve a new empirical claim or public deployment.

Use small vertical slices with explicit acceptance criteria.
Record decisions, verification, failures and blockers with each batch.
When external evidence is missing, record the blocker and continue independent work.

## Preserved boundaries

Preserve existing saves, deterministic replay and frozen historical models.
Version new behaviour that changes simulation results; preserve dispatch for supported historical versions.
Keep research behind separate entrypoints and preserve its declared limits.
Do not claim empirical validation or invent historical evidence.
Do not purchase services, deploy publicly, delete owner data or promote research models without separate approval.
Do not expose controls whose effects the active model disables.

## Decisions requiring owner input

Ask only when a decision is irreversible, materially changes product scope or needs unavailable information.
Existing authorisation remains valid across sessions; do not request it again for routine work.
External evidence is a factual requirement, not an approval that can be inferred from elapsed time.
Continue unrelated authorised work while evidence remains unavailable.

## Execution and continuity

The agent works autonomously during an active session.
This brief does not establish a background service or promise execution between sessions.
`V01_DELIVERY_PLAN.md` and `V01_BACKLOG.json` hold the persistent work queue.
`CURRENT_STATUS.md` holds implemented capability and acceptance boundaries.
`NEXT_PASS.md` identifies the next eligible slice.

Each session starts from the existing queue and preserves completed work.
The agent reports completed batches, actual test results, decisions and remaining blockers.
It does not request approval between ordinary implementation steps.
